  1. GESTIÓN DE DATOS: ERAS en la DB JSON de Drive
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ESQUEMA DE LA DB (EMPTY_DB en GoogleDriveService.js)
  ──────────────────────────────────────────────────────
  El archivo "the_vault_database.json" vive en appDataFolder de Drive.
  La clave "eras" es un array de objetos con este shape real:

    {
      id:          string (uuid v4),
      name:        string,
      description: string,
      start_date:  ISO string,
      end_date:    ISO string | null,
      color:       string (hex),
      cover_image: string | null,   ← URL o base64. Aún SIN subida real.
      created_at:  ISO string
    }

  FLUJO COMPLETO de fetchData() para Eras
  ──────────────────────────────────────────────────────
  Paso 1 → fetchData() llama a _findDatabaseFile()
           Busca en appDataFolder el archivo con name = 'the_vault_database.json'
           Cachea el fileId en _state.dbFileId para no repetir la query.

  Paso 2 → _readDatabaseFile(fileId)
           Llama a drive.files.get({ fileId, alt: "media" })
           Parsea el body como JSON.
           Retorna el objeto completo, incluyendo el array db.eras.

  Paso 3 → VaultContext recibe el objeto en initDatabase() / refreshDb()
           Lo guarda en el estado React `db`.
           Vault.jsx lee `db.eras` directamente vía prop db.

  Escritura de Eras (addEra / updateEra):
  ──────────────────────────────────────────────────────
  addEra(eraData)  → updateData(updater)
                   → read-modify-write: lee la DB, hace spread, escribe.
                   → PATCH multipart al endpoint de Drive API v3.

  updateEra(eraId, patch) → mismo patrón read-modify-write.

  VEREDICTO: La lógica de persistencia de Eras en Drive está
  COMPLETAMENTE IMPLEMENTADA y es funcional.
  El campo cover_image existe en el schema, pero su valor
  se guarda como URL/string — no hay lógica de subida binaria
  de imágenes a Drive todavía (ver sección 4).

  ──────────────────────────────────────────────────────
  ✅ Ver el slider horizontal de Eras (con datos reales de db.eras)
  ✅ Seleccionar una Era activa (estado local React, setActiveEraId)

  3. REAL vs DEMO — DATOS HARDCODED EN VAULT.JSX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ELEMENTO 1: displayEras (Eras del slider)
  ──────────────────────────────────────────────────────
  ESTADO: HÍBRIDO — SEMI-DEMO

  Lógica:
    const eras = (db?.eras ?? []).map(...)
    const displayEras = eras.length > 0 ? eras : [ DEMO_ERAS ]

  Si db.eras tiene datos reales → muestra datos reales. ✅
  Si db.eras está vacío (usuario nuevo) → cae en los tres objetos
  hardcoded: "ORIGEN", "TORMENTA", "RENACIMIENTO". ❌ DEMO
  Estos datos demo NO se guardan en Drive. Son puramente visuales.
  El usuario los ve, interactúa con ellos, pero no existe botón para
  convertirlos en Eras reales.

  Líneas afectadas en Vault.jsx (bloque displayEras):
    [ id: "demo-1", name: "ORIGEN", ... ]
    [ id: "demo-2", name: "TORMENTA", ... ]
    [ id: "demo-3", name: "RENACIMIENTO", ... ]

  ──────────────────────────────────────────────────────
  ELEMENTO 2: demoTimeCapsules (Cápsulas del Tiempo)
  ──────────────────────────────────────────────────────
  ESTADO: 100% HARDCODED — DEMO PURO ❌

  El array demoTimeCapsules está declarado directamente en el
  render de Vault.jsx y no tiene ninguna conexión con la DB:

    const demoTimeCapsules = [
      { id: "tc-1", title: "CARTA AL FUTURO",    unlockDate: Date.now() + 90d },
      { id: "tc-2", title: "PRIMER ANIVERSARIO", unlockDate: Date.now() - 10d },
    ]

  - No se lee de db.entries (donde vivirían con type: "letter" o similar)
  - No se guarda en Drive
  - El unlock ya está desbloqueado en "tc-2" solo visualmente
  - No hay forma de que el usuario cree, edite o borre cápsulas reales
  - El contenido del unlocked ("Ya pasó un año. Lo logramos.") es texto fijo

  IMPACTO: Toda la sección de Cápsulas del Tiempo es decorativa.

  ──────────────────────────────────────────────────────
  ELEMENTO 3: db prop = null (fallback)
  ──────────────────────────────────────────────────────
  ESTADO: FALLBACK CONTROLADO — NO ROMPE ✅

  AdventureCounter: usa db?.adventures_start_date ?? Date.now()-500d
  HeartbeatWidget:  usa db?.heartbeat ?? new Date().toISOString()
  EraDetailPanel:   usa db?.entries ?? []

  Los fallbacks son seguros y no muestran datos inventados como si
  fueran reales. Correcto comportamiento defensivo.

  4. INTEGRIDAD DEL SISTEMA HEARTBEAT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  HEARTBEAT DE CUENTA PRINCIPAL (db.heartbeat)
  ──────────────────────────────────────────────────────
  ¿Es real o solo visual? → REAL Y FUNCIONAL ✅

  Mecanismo completo verificado:

  1. Al hacer login → requestAccessToken() llama a _triggerHeartbeat()
     automáticamente tras obtener el token.

  2. VaultContext._scheduleHeartbeat() → setInterval de 20 min
     que llama a triggerHeartbeat() mientras la sesión está activa.

  3. Page Visibility API → cuando el usuario vuelve a la pestaña
     (visibilitychange = "visible"), se dispara heartbeat() manual.

  4. _triggerHeartbeat() en GoogleDriveService:
     - Tiene throttle real de 15 min (HEARTBEAT_THROTTLE_MS)
     - Lee la DB de Drive, actualiza el campo `heartbeat` con
       new Date().toISOString(), y escribe de vuelta con PATCH.
     - Falla silenciosamente (console.warn) para no crashear la UI.

  5. HeartbeatWidget lee db.heartbeat (dato real) y calcula
     monthsSince() para determinar si está en riesgo.
     El umbral visual (20 meses) está alineado con la lógica
     de bibliotecas (LIBRARY_AT_RISK_MONTHS = 18 meses en Config).
     ⚠ Discrepancia menor: el widget usa 20 meses como umbral visual,
     pero el servicio marca at_risk a los 18. Sincronizar.

  HEARTBEAT DE BIBLIOTECAS (last_heartbeat_check)
  ──────────────────────────────────────────────────────
  ¿Protege realmente las cuentas de fotos? → PARCIALMENTE REAL ⚠

  Lo que SÍ funciona:
  ✅ markLibraryHeartbeat(id) → escribe last_heartbeat_check en Drive
  ✅ _calcLibraryStatus() calcula at_risk/lost solo con aritmética de fechas
  ✅ librariesAtRisk y librariesLost se derivan automáticamente en el contexto
  ✅ refreshLibraryCapacity() llama a Drive API real para medir uso en GB
  ✅ listLibraryContents() pagina automáticamente carpetas compartidas reales

  Lo que NO funciona / falta:
  ❌ No hay UI en Vault.jsx para mostrar las bibliotecas ni su estado
  ❌ No hay alerta visual cuando librariesAtRisk.length > 0 en este módulo
  ❌ El admin debe pulsar manualmente "acabo de entrar a esta cuenta" —
     no hay verificación automática de que la cuenta siga activa
  ❌ checkLibraryCapacity no se llama automáticamente al arrancar
     (solo cuando el usuario lo solicita explícitamente)
